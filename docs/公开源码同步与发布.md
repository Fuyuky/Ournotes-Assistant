# 公开源码同步与发布

公开仓库为 `Fuyuky/Ournotes-Assistant`。公开 checkout 和带私有运行数据、旧 Git 历史的开发工作区须分开保存。初始公开提交是当前源码的白名单快照，没有原开发仓库的提交历史。

## 后续同步

1. 先在开发工作区检查状态并保留全部未提交工作，再从公开仓库的独立 checkout 创建 `codex/` 分支。原工作区即使 origin 指向公开仓库，也不能直接 push、merge、cherry-pick、导入 bundle 或复制 `.git`；这些动作可能把旧私有历史一起上传。
2. 以公开 checkout 当前已跟踪的文件清单为起点，从开发工作区复制需要更新的源文件。新增文件必须先补入明确白名单并审查；消失的文件只在公开 checkout 中逐项确认后 `git rm`。不要在原开发工作区 reset、checkout、read-tree 或 clean 来制造公开状态。
3. 可复制客户端与云端 Python 源码、网页源码、合成测试、应用默认配置、部署示例、正式构建/维护入口和已核验的原生控件/卡牌裁切。仍排除状态、账号、结果、日志、机器配置、所有凭据、下载图集、私有回归证据、完整运行截图、首次 OAuth 工具、旧商品工具和固定本机路径的临时清理脚本。
4. 在公开 checkout 查看 diff 与待提交文件，扫描邮箱、私钥、令牌、密钥、私有服务器配置和截图；测试数据须为合成样例。检查 `.gitignore` 之外还要检查 Git 已跟踪路径，忽略规则不能撤回已被跟踪的文件或旧提交。
5. 使用 `uv.lock` 对应环境运行本次改动相关的合成测试。完整视觉回归需要私有 fixture，要求见[公开源码与测试素材](公开源码与测试素材.md)；未执行的实机或视觉验收须明示。
6. 仅从公开 checkout 提交和推送；提交身份使用 GitHub noreply 邮箱。推送后核对远端分支 SHA，并通过匿名 GitHub 页面/API确认源码可读。保留原开发工作区的状态与私有历史。

可从公开 checkout 列出允许同步的已跟踪路径：

```powershell
git -C <公开checkout> ls-files
git -C <公开checkout> status --short
git -C <公开checkout> diff --stat
```

这些检查与复制源文件都不需要启动模拟器、读取生产邮箱、恢复批次或改数据库。

## Release

源码公开和 Release 发布分别核验。SSH Git 推送权限不代表存在创建 Release 的 API认证。使用正常 GitHub网页登录或在本机完成 `gh auth login` 后，再按[客户端构建与更新](客户端构建与更新.md)准备并发布；不要在聊天中提供 PAT 或其他秘密。

生产 Ed25519 私钥在项目之外单独保存、访问控制并备份，以后复用同一密钥，发行包只携带公钥。当前以临时测试密钥生成、标有 TESTONLY 的验收包不能发布为正式 Release。发布前分别核验初装包、更新包、平台清单、签名、摘要及明确完成的实机检查。
