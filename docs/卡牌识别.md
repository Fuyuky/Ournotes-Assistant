# 卡牌结算识别

运行唯一结果来源是稳定的结算截图，原图与哈希先进入持久后台队列；账号恢复复用原素材版本和缓存。已提交缺失结算证据不能补抽。识别实现 `ournotes/vision/recognition.py`，队列 `ournotes/runtime/recognition_queue.py`，只在本机处理，不读取邮箱或调用LLM。

卡牌为 `kind:id`，角色与支援同数字ID不能合并。目录中的R/SR/SSR都参与识别，展示汇总过滤R，不能把R强制分入高稀有度。元数据/图片和哈希以账号固定BDON目录为准，不在文档固化卡牌张数；网站素材与运行快照独立，更新不替换已分配账号的原版本。

离线工具读取结算截图，逐槽保存布局、身份、候选差距、几何/图像指标、算法版本、素材清单哈希和截图哈希；不完整结果明确标为部分，不能进入成功样本。相同输入字节不得重复计数，同交易不同动画帧也不能当两笔。Python可调用CardRecognizer复用实例，不要求文件名携带池名或抽数。

## 如何处理首次与重复抽取

先统一到1600×900坐标，检查“招募结算”和“招募TOP”，再根据画面纹理检查单抽/十连布局。十连按画面10个槽逐个识别，单抽取居中槽。这里的结果槽位置不表示卡池序号，不依赖卡池数量或其顺序。

标题、按钮和连续两帧稳定不能证明卡面已经下载完成。`ResultLayout` 还检查结果槽中的加载圆圈；素材为 `settlement-templates/manifest.json` 中的 `kind=result_loading` 原生裁切，覆盖角色卡、支援卡和光效外观，按有限旋转匹配。任何槽仍在加载时抛出 `ResultLoading`，Observer 返回无可点击结算控件的 loading 状态，DrawFlow 等待后续画面，不保存占位图、不退出原结算页。圆圈消失后仍须通过原有布局及两帧稳定检查；持续加载沿用未决交易的暂停保护，不重启或补抽。

每个槽只读取上半部未遮挡的卡面：相对槽左边 `x+10..x+140`，全屏 `y=225..450`。先裁剪，再提取SIFT特征，因此特征描述也接触不到上方NEW/属性标记、下方碎片150、稀有度文字。首次与重复的区别不作为分类输入，也不输出“是否首次”。

当前固定目录的全部原素材参与候选匹配，R同样识别；最后才过滤R，避免R被强行归入SR/SSR。SIFT匹配后用RANSAC检验几何一致性，再检查覆盖范围、灰度/局部细节相关性与候选差距。留影的旋转和透视由几何匹配处理，较宽的光效用局部细节比较补充。方法参考 [OpenCV特征匹配与单应变换说明](https://docs.opencv.org/4.x/d1/de0/tutorial_py_feature_homography.html)。

当前拒识条件包括有效匹配点不足14、内点比例不足0.55、覆盖/分布不足、图像相关性不足0.5、前两候选不够分离。各项是判定指标，不是识别正确率百分比。最强几何候选未通过时不改选较弱身份；素材缺失、模糊或歧义返回 `unknown`。

SSR 边缘光效复核保留单次 16 像素裁切的高置信度分支；边缘裁切仅通过普通阈值时，要求另一固定 12 像素裁切独立通过相同身份校验。不能通过裁切搜索解决素材缺失或身份歧义。

对于边缘裁切也无法匹配的局部强光，固定把安全卡面区内部划成 2 列、3 行。只让素材覆盖达到 85% 的区域参加校验；至少四区有效，至少三区且不低于有效区的 75% 达到 0.65 相关性。通过区域还必须覆盖卡面裁图的 35%、素材共同区域的 45%，并具有至少 14 个分布在两行两列、至少三区的几何特征点。只复核全图的同一强候选，所有具备几何支持的竞争身份都参与差距检查。大量遮挡、只剩一小片相似背景、素材缺失或重复身份仍返回 `unknown`。

区域边界固定，不能不断改变裁切位置寻找一个偶然吻合；原边缘交叉校验发生冲突或失败时也不能靠区域分支覆盖。输出的 `regional_verification` 保留各区坐标、相关性、覆盖率和特征分布；整张识别结果还记录 `recognizer_version` 和 `catalog_sha256`。持久化缓存按原截图哈希复用，复核保留原耗时与审计，不自动重算或改写账号。

## 失败截图作为匹配素材

以后识别失败，先核对失败类型与截图中的对象，再用该次失败截图的原生像素裁切更新对应参考素材。统一清单位于 `ournotes/vision/assets/settlement-templates/manifest.json`，加载器为 `ournotes/vision/templates.py`。清单记录来源图和裁图 SHA-256、原图尺寸、裁切坐标及核验说明；未核验、哈希错误、越界或尺寸不符的条目拒绝加载。

`kind=card` 条目需要 `key=kind:id` 与核验时的 `catalog_card_sha256`，替换该身份原有的 BDON 参考图。账号固定目录不含该身份、排除该身份或素材哈希已改变时，不使用此裁图。卡牌仍需通过原有几何、图像一致性与候选差距检查；匹配结果附带 `template_source`。无法确定身份时保留待复核，不能把首候选自动作为标签，也不能把来源截图匹配自己当成独立验证。

`kind=result_button` 条目用于已核实的招募 TOP 控件外观，记录 `side` 与 `state`。正常/按压外观分别匹配，标题、结果布局与前景亮度校验保持有效；模板仅裁按钮，排除周围动画。已保存结算的交易遇按压停留时记录一次触摸释放，等待明确页面状态，不能点击“再次招募”或重新提交交易。

更新模板后，使用另一帧或另一交易进行交叉验证，并检查变暗、遮挡、错误按钮和身份歧义仍被拒识。运行中的旧识别器保留已加载素材；通过安全暂停与原批次恢复加载更新，沿用交易和缓存。

## 适用边界与验证

当前国际服简中、稳定1抽/10抽、完整16:9画面，尺寸至少960×540且不含模拟器边框。其他语言、UI布局或抽数布局须补真实样本。动画、遮挡、压缩或目录未收录返回unknown；只允许复核已有证据，不为报告补拍或重抽。

保存的实拍回归样本与逐槽独立标签在 `tests/test_recognition.py`，覆盖首次/重复、多张相同卡、NEW/碎片/稀有度遮挡、缩放/变暗、非结算页、噪声、缺素材、重复身份、重复输入和损坏素材。光效样本在 `assets/reference/runtime-regressions/artwork-glow`，模板加载有来源哈希与独立样本交叉验证。测试证明这些样本及变体的行为，不代表所有未来卡面/UI版本。

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest tests/test_recognition.py tests/test_async_pipeline.py -q
```

`assets/reference`与`data/bdon`是回归依赖，不作为日志清理。美术来源为 [BDON](https://bdon.moe/)；主数据来自 [moenotes-masterdata](https://github.com/StarMoe-org/moenotes-masterdata) 的 `hk-tw-mo`。`catalogs/masterdata.py` 从同一份 Git 归档读取全部所需表，核验区域、版本清单哈希及表身份，记录提交号、客户端和资源版本；不回落到其他服务器。`scripts/update_bdon.py` 完成卡牌、卡池图片及引用校验后才切换运行快照，失败保留旧指针，已分配账号继续引用原目录。网站素材仍经独立入口更新。运行与故障核验见 [运行与恢复](运行与恢复.md)，控件页面识别见 [UI框架](UI识别框架.md)。
